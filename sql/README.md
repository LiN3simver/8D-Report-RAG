# 查詢層設計重點

> 實際的 SQL 查詢檔屬於內部資料，不包含在展示版中；本文件只說明查詢的設計。

## 檔案組織：分段組裝、欄位對照只有一份

查詢檔以 `-- @區塊名` 分段，由 [src/car.py](../src/car.py) 依需要組裝：

| 區塊 | 用途 |
|---|---|
| `@columns` / `@from` | 一張單的全部欄位與 JOIN。「查單張」與「查清單」**共用**，欄位對照不會在兩處漂移 |
| `@detail_where` / `@by_ids` | 單張查詢、依 id 清單撈整列 |
| `@parts` / `@notify` | 關聯料號、通知人員 |
| `@by_part_ids` | 料號反查（兩條路 UNION） |
| `@stats_*` | 成立與否、狀態、廠區、申請種類、客戶、異常歸類、期間的統計 |

過濾條件由 Python 端產生一段共用的 `WHERE`，只引用主表欄位或子查詢、不依賴 JOIN 別名，
因此同一段條件可同時套用到清單查詢與所有統計區塊。所有值都走參數綁定，不做字串拼接。

## 資料層的陷阱與對策

| 陷阱 | 對策 |
|---|---|
| **Discipline 欄位名與內容錯位一格**：名為 containment 的欄位裝根本原因、名為 root_cause 的欄位裝臨時對策 | 依表單 label（而非欄位名）建立別名；對照集中在 [src/fields.py](../src/fields.py)，selftest 以內容斷言守住 |
| **清單值的多語系 label** 存在值本身的多個欄位，部分語系為 NULL | 一律「繁中 → 英文 → 原值」依序取第一個有值的 |
| **兩個廠區清單不同碼**（同一廠區在兩份清單的代碼不同） | 生產廠區與填單／責任廠區分別 JOIN 各自的清單，不可互換 |
| **退役代碼**：清單已刪除、但舊單仍在使用的代碼 | 生產廠區三層解析：清單 label → 畫面快取欄位 → 裸代碼，舊單仍顯示得出來 |
| **料號登記在兩個地方**，約 7% 的單只有文字欄 | 「關聯表精確比對」UNION「文字欄子字串比對」，每筆標示 `matched_by` |
| **「是否成立」的 NULL** 代表尚未判定 | 統計時 NULL 自成一組，成立率分母只算已判定 |
| **多值欄位**以逗號分隔 | 拉回 Python 端拆解計數，不依賴資料庫的字串分割函式與相容性設定 |
| **JOIN 放大列數**的風險（ON 條件寫寬時每列看起來都合理） | 每個 JOIN 都是一對一；selftest 比對 JOIN 前後的列數 |
| **填答率 0% 的欄位、虛擬屬性** | 不放進查詢，避免多餘的 NULL 與「無效的資料行名稱」錯誤 |

## 安全與效能

- 唯讀帳號、只執行 SELECT；連線設定登入逾時與查詢逾時（pyodbc 預設為永不逾時）。
- 列數硬上限，避免空白關鍵字把整庫倒進 LLM context。
- 語料規模小（數百張單），全表文字欄 LIKE 掃描約 12ms，因此不建向量索引、不落地。
